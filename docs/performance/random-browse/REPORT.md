# 随便逛逛：选房与切房响应优化

日期：2026-10-20。以游岚 YolanLive v1.0.8 的随机浏览实现为基线；保留本地已选 D1 图标，版本号仍为 1.0.8。本轮只交付源码与本地完整预览目录，不生成安装包、便携 ZIP 或发布 GitHub。

后续交付：用户确认发布后，以上源码与按钮修复纳入 v1.0.9；正式构建、软件包及发布验证另见 [v1.0.9 发布检查](../../validation/release-1.0.9.md)。下文保留原预览时的测量条件和失败记录。

## 改动

- 选择同一平台的游戏首页候选时，先处理已返回的分区；不再等待所有分区才能确认房间，选中后取消其他请求。四个平台仍先打乱顺序后依次尝试，不使用四平台抢答方式改变随机规则。
- 候选按平台保存在内存，30 秒失效，每个平台最多 24 条、最多四个平台；按需清理和淘汰，没有新增磁盘缓存或轮询计时器。排除本轮已访问房间，确认停播时从候选中移除。
- 用一次房间详情获取合并选房阶段的开播确认，播放器接收同一次选择的详情；只允许同平台、同房间且 15 秒内的详情复用，过期或不匹配则重新取。画质与播放地址仍在实际打开时获取。
- 实际播放器进入 Playing 后，每个随机会话最多保留一项“下一间”预取任务，仅取游戏候选和房间详情，不主动获取画质、播放地址，不下载视频，也不创建第二个播放器。
- 预取结果不写观看历史、不改变当前位置；点击下一间才使用，过期先重新确认。回到历史中间不预取新的随机房间；预取失败不打断当前播放或更改账号状态，前进时可以重试。
- 结束会话、关闭/离开页面或取消等待会取消相关请求；本轮最多 60 秒、每个平台 12 秒、历史详情检查 10 秒的预算保留。预先取消的导航不能绕过快速路径启动新的画质或地址请求。
- 公共数据请求并发上限 4、签名浏览器串行与空闲回收规则不变；没有增加线程/内存硬上限，没有调整画质、解码或缓冲参数。平台接口 ILiveSite 与普通打开直播的调用保持兼容。

## 补充：随机切换后前后按钮锁住

用户报告点击下一间后两按钮持续置灰。普通前进、后退的实际播放器页面测试通过；使用本地 HTTP/H.264 和可控平台，令下一间画质请求收到取消但继续等待，复现按钮无法恢复（[失败记录](buttons-red.txt)）。这证明了一条可导致同样症状的路径，不代表已捕获用户现场的具体网络请求。

修正房间加载的详情、画质与随机选房详情的等待边界：继续向底层传递取消信号，同时由等待方遵守已有超时，不依赖平台任务何时返回。没有缩短原超时、增加请求或轮询；过期结果不能进入播放流程。切换中仍禁用按钮，首间仍禁用上一个。

历史详情取消用例同样先失败再修复（[失败](buttons-detail-red.txt)、[通过](buttons-detail-green.txt)）。底层取消断言继续保留；由于调用方现在可先退出等待，相关夹具改为显式等待底层取消完成信号，避免把线程调度顺序误判为取消失效。正常往返、重复操作防护、超时恢复与迟到结果抑制由实际页面按钮测试覆盖。

最终预览验证：实际播放器页面 6 项检查通过（[记录](buttons-final-random-browse-checks.txt)），现有性能回归 6 组通过（[记录](buttons-final-performance-checks.txt)），随机浏览辅助检查 10 项通过。原取消顺序失败记录保留在 [buttons-cancel-order-red.txt](buttons-cancel-order-red.txt)。未重新测量真实平台首帧或长期性能，未打包、未发布。

## 可控前后对照

使用同一个本地替身：一个游戏分区 40ms 返回有效房间，其他分区 800ms 返回；单次详情 120ms。基线使用已发布 v1.0.8 的原 RandomLive 源文件；优化版使用当前源码。两个独立进程各运行冷启动一次及后续两次，均不播放视频。

| 指标 | 原版 | 优化版 |
| --- | ---: | ---: |
| 第一次选房＋详情 | 1069.2ms | 205.1ms |
| 第二次 | 1061.2ms | 124.0ms |
| 第三次 | 1053.5ms | 124.8ms |
| 三次游戏首页分区请求 | 9 | 3 |
| 三次详情请求 | 6 | 3 |
| 独立开播状态方法调用 | 3 | 0（由详情确认） |

[原版原始数据](baseline-metadata.json)、[优化版原始数据](optimized-metadata.json)。这些结果证明避免等待和请求复用在该受控场景中有效，不是用户真实网络、首帧、CPU 或内存的提速比例。状态方法在本替身中内部获取详情，不应把状态与详情计数重复相加。

## 隔离访客实测与限制

使用 D 盘新的访客目录，未加载日常 Cookie、浏览器资料、关注或历史；每个平台独立尝试一次，采用当前默认画质偏好和首条返回线路。[原记录](visitor-live.txt)。

| 平台 | 本次结果 |
| --- | --- |
| 哔哩哔哩 | 访客选房失败，789ms，InvalidOperationException；本轮未修复此接口失败 |
| 抖音 | 选房含详情 10521ms，画质 2ms、地址不足 1ms，解码就绪 402ms |
| 虎牙 | 所选首条线路解码初始化失败，232ms，COMException；未验证所有线路 |
| 斗鱼 | 选房含详情 594ms，画质 2639ms、地址 640ms，解码就绪 441ms |

“解码就绪”仅表示 MediaPlayer 处于 Playing 且存在视频宽度，不是屏幕实际首个像素的测量；这组真实平台测试没有同房间、同网络的原版对照，不能据此宣称四平台全面通过或真实首帧全面加速。

预取只在随机房间已经开始播放后触发，所以第一次点击、平台冷启动、浏览器被空闲回收以及过期详情重新确认仍可能有等待。收益主要来自减少挑房阻塞、重复接口请求和后续切房的前台准备工作；平台自身请求、画质签名及视频网络缓冲仍可能成为瓶颈。
